# option.sell 需求文档（v2 重写基线）

> 本文是 `option.sell`（期权卖方策略）重写版的需求基线，**全新设计，不沿用旧系统的文档 / 代码 / 数据**。
> 旧系统 `strategies/sell_option` 经运行发现较多问题，仅作背景了解，待新系统完成后即删除；本文面向重写，聚焦 v2 目标与必须规避的 v1 陷阱。
> 标注「待定 / 待你拍板」处为尚未确定的设计，随重写推进填充。

## 一、背景与目标
- v1（`strategies/sell_option`）运行后发现较多问题 → 停止维护，本目录从零重写（旧文档/代码/数据均不沿用，仅作参考）。
- 目标：一个**只读决策支持工具**——数据分析 + 生成报告 + 交易提醒（事件 / 长假 / 破位 / 到期）。
- 不接账户、不下单、不自动交易；人工看报告自行决策与下单。
- 范围：期权卖方**垂直价差 / 铁鹰**（带保护腿、封顶、绝不裸卖）。

## 二、必须坚守的域约束（v2 重新实现，不照搬旧代码）
> 以下是从 v1 踩坑中沉淀的**通用域规则**（与具体实现无关），v2 必须以全新代码满足，而非复制旧实现。
1. **价格口径两分，绝不混用**：连续指数（后复权）只用于相对指标（收益率/波动率/趋势/ADX/区间位置）；真实月份合约（不复权）用于一切绝对价（现价/行权价/权利金/保证金/安全垫/封顶/肥瘦）。混用即缺陷。
2. **缺数如实判 MISSING**，绝不用代理数据冒充、不静默降级成 PASS。
3. **绝不裸卖**，全部封顶价差；单笔最大亏损 =（价差宽度 − 净权利金）× 乘数，封死。
4. **取数归属交易日（pull_date）统一口径**：缓存按最近交易日严格查/落，跨日自动失效，不拿旧数据冒充新决策；盘中实时价不缓存。
5. **离线/缓存模式产物必须打时间戳**，避免误当实时。

## 三、v1 已知问题（v2 必须规避）
- **数据维护时机错位**：数据在"生成报表时才去拉取"，拉取与报表强耦合。数据源一不稳，报表质量直接被拉垮，且无法在数据层先发现问题。
- **脏数据检不出**：持仓 / 行情等表存在脏数据，旧流程缺独立的质检环节，检查逻辑照单全收 → 结论失真。
- **缺失 / 非终态数据无法维护**：拉到的数据可能缺失，或并非终态（盘后未结算、盘中实时未定稿）；旧流程无机制判断"数据是否可用、是否已定稿"，直接拿去出报表。
- **根因**：拉取、质检、出报混在同一时机，缺少阶段隔离与数据就绪门禁。v2 解法见 §六「三阶段流水线」+ §6.5 中央就绪登记表。

## 四、产品定位（方向性，v2 自行定义）
- 只读决策支持；"可开 / 不可开"仅是机械化检查结论，非投资建议；下单前人工复核盘口与保证金实数。

## 五、策略核心（方向性，v2 自行定义）
- 适用场景：震荡市收取时间价值 + 波动率下降收益。
- 卖平值/虚值价差（收时间价值）+ 买入更虚值保护腿（预防单边风险）→ 垂直价差 / 铁鹰。
- **单卖**＝一侧垂直价差（2 腿）；**双卖/铁鹰**＝上下两侧价差（4 腿）＝两个单卖；均带保护腿、最大亏损封死、不做任何裸卖。

## 六、数据治理：三阶段流水线（核心架构）
> v2 必须将数据生命周期拆成三个**相互独立、可单独运行、阶段间用门禁隔离**的阶段，彻底解决 v1「报表时才拉数据 → 脏 / 缺 / 非终态数据直接污染结论」的隐患。阶段三**不得**在阶段二未通过时运行。

### 6.1 阶段一：拉取数据（fetch / prefetch）
- 与报表**解耦**：拉取不绑定报表生成，可独立、可定时（如盘前 / 盘后预取）运行，结果落本地缓存（sqlite / JSON）。
- 多源取数失败逐源降级、不崩；断点续取；按 `pull_date` 归属交易日严格缓存（承接 §二.4）。
- **拉取只负责"拿回来"，不做任何业务判定。**
- 每完成一个数据表的拉取，即向**中央就绪登记表**（§6.5）写入 / 更新该表记录（status: fetching → pending_validation），供阶段二 / 三统一监控。

### 6.2 阶段二：检查数据（validate / quality gate）—— v1 缺失的关键环节
- 在数据进入策略逻辑前，先对缓存做**质量校验**，结果回写**中央就绪登记表**（status: ready / incomplete / dirty / non_terminal + 指标计数），作为阶段三门禁的唯一事实来源。
- 校验维度（具体规则 / 阈值待细化，但本阶段必须存在）：
  - **完整性**：必填字段 / 数据项是否齐全（依赖 §6.5 数据契约的 `expected_n` 判定），缺失 → 标记 MISSING，不进报表；
  - **脏数据**：数值越界、符号异常、重复 / 冲突记录、口径串用（指数价当真实价等，承接 §二.1）的静态规则检出；
  - **终态性**：数据是否已是终态 / 已结算（如盘后行情是否定稿、当日是否收盘），非终态明确标注、不混入终态结论；
  - **一致性**：跨源（tbpy / openvlab / 新浪）对同一标的的取值是否冲突，冲突以权威源为准并报警。

### 6.3 阶段三：生成报表（report）
- 仅消费阶段二判定为「ready」的数据；对「缺失 / 脏 / 非终态」项，报表如实标注（MISSING / 待复核），**绝不拿未过检数据硬出结论**。
- 报表本身不含取数逻辑，纯消费已质检数据。

### 6.4 门禁（gate）
- 阶段三**不可**在阶段二未通过时运行；可先单独跑阶段一 + 二产出「数据就绪报告」，再决定是否跑阶段三。
- 门禁判定依据 = **中央就绪登记表**（§6.5）中对应数据表是否 `status=ready`；登记表本身持久化，可随时查询「某交易日各表准备情况」。
- 离线模式（纯缓存运行）同样须先过阶段二质检，缺失 / 非终态项照常标注、打时间戳（承接 §二.5）。

### 6.5 中央就绪登记表（整体管理 / 监控）
> v2 数据落地方式：**全部数据统一存入单一库文件 `option.db`**（不再一表一库；业务表与控制面表同库、以表逻辑区分，表名见 `库表设计.md` §一 / §二）；其中**中央就绪登记表** `data_readiness` 整体管理与监控每一张业务数据表的准备情况。它是 §6.4 门禁的唯一事实来源，也是"数据就绪报告"的数据底座。

```sql
-- option.db（业务表与控制面表同库、逻辑分表）
CREATE TABLE data_readiness (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    source_key      TEXT,    -- 逻辑名：daily / spot / premium / iv / calendar / positions / option_index ...
    table_ref       TEXT,    -- 实际落库位置：如 'daily.db:history' 或文件名
    source          TEXT,    -- tbpy / openvlab / sina / manual
    pull_date       TEXT,    -- 归属交易日（同 §二.4）
    phase           TEXT,    -- fetch / validate / report（当前所处阶段）
    status          TEXT,    -- pending / fetching / ready / incomplete / dirty / non_terminal / error
    expected_n      INTEGER, -- 应到条目数（由 §七 契约 expect_scope 动态枚举算得，非静态列）
    actual_n        INTEGER, -- 实际条目数
    missing_fields  INTEGER, -- 缺字段计数
    dirty_n         INTEGER, -- 脏数据计数
    non_terminal_n  INTEGER, -- 非终态计数
    last_fetch_at   TEXT,    -- ISO 时间戳
    last_validate_at TEXT,
    note            TEXT
);
```

- **监控视图**：按 `pull_date` 查询即得「该交易日各表 status」总览——哪张表 ready、哪张缺数/脏/非终态，一目了然（即 v1 缺失的"整体数据准备看板"）。
- **依赖应有清单（§七）**：就绪表的 `expected_n`（应到）由 §七 契约的 `expect_scope` **动态枚举应有实体**算得（非静态列），是"完整性"判定的前提；无清单则完整性只能查单条格式、查不出"整个品种/表没拉到"。注意：就绪表只反映"已被拉取/校验的表"状态——若某品种/表根本没被拉取（静默漏掉），就绪表里可能压根没有它的行，此时必须拿就绪表与应有清单**对账**才能发现"整张表/整个品种缺失"。单有就绪表不够，这正是 §七 应有清单存在的意义。
- **派生产物**：阶段二结束后，据此表生成人类可读「数据就绪报告」（承接前文 D 块），告知用户"为什么这份报告是残的"。

### 6.6 全局配置表
> 系统级**固定配置**统一收口到一张表，避免散落在代码常量 / 环境变量里、难维护难审计。与 §6.5 就绪表（运行态）、§七 应有清单（数据契约）并列，三者同置于 `option.db`、共同构成**控制面**。

- 形态建议：扁平 key/value，分组以 key 前缀体现（如 `source.` / `schedule.` / `gate.`）：

```sql
-- option.db
CREATE TABLE 全局配置表 (
    key         TEXT PRIMARY KEY,  -- 配置项名（含分组前缀，如 source.tbpy_priority）
    value       TEXT,              -- 配置值
    remark      TEXT,              -- 说明
    create_time TEXT,              -- 创建时间 YYYY-MM-DD HH:MM:SS
    update_time TEXT               -- 最后更新时间 YYYY-MM-DD HH:MM:SS
);
```

- 候选内容（"全局配置的、固定的东西"，待你拍板具体项）：
  - `source`：各数据源优先级与降级顺序（如 tbpy=1 / openvlab=2 / 新浪=3）、限流 / 超时；
  - `schedule`：预取时机（盘前 / 盘后）、各表刷新频率；
  - `gate`：门禁严格度（阶段三是否要求全部 ready 才可跑、还是允许部分降级）；
  - `mode`：离线模式默认开关、缓存失效策略；
  - `notify`：事件 / 长假 / 破位 / 到期提醒的投递目标（邮件 / 微信等）；
  - `path`：各业务 db 的存放根路径；
  - `threshold`：全局默认阈值（IV 分位下限、单笔保证金上限等；**逐品种覆盖值放 §七 应有清单 / 品种边界表**）。
- **职责区分**：全局配置表 = "系统怎么跑"（固定开关 / 参数）；应有清单 = "该有哪些数据"（数据契约）；就绪表 = "数据现在怎样"（运行态）。三者不重叠。
- 注意：逐品种的固定参数（乘数 / 保证金率 / 组合优惠，即 v2 新版**品种边界表**）属于"逐品种固定"，建议单列 `product_boundary` 表，**不要塞进全局配置表**，避免全局表变成万物桶。

## 七、应有清单（数据契约 / 阶段零）
> **关键洞察**：§6.5 的就绪表只反映"已被拉取/校验的表"的状态；若某品种/数据表根本没被拉取（静默漏掉、或被源跳过），就绪表里可能压根没有它的行——单有就绪表**发现不了"整张表/整个品种缺失"**。因此必须另有一张**应有清单**定义"本应存在什么"，两者对账才能覆盖 缺失 / 脏 / 非终态 全部三类问题。
> 应有清单 = **期望维度（静态/配置）**，是"标准答案"；就绪表 = **实际维度（运行态）**，是"实时考卷"。两者的关系：
> - **完整性** = 对应有清单每一项，就绪表里是否存在对应行且 `status=ready`；无行或 ≠ready → 该项缺失/未完成。
> - **终态性** = 应有清单为每项标注"终态条件"，就绪表据以判定数据是否已定稿。

- 新品种边界表（v2 自建，不沿用旧 `品种边界表.md` 实数）：品种清单、symbol 编码、乘数、保证金率、组合优惠等静态参数；
- 每个**取数单元（馈送）**的取数契约：权威源与降级链 / 分档 / 频率与时机 / 窗口条数 / 落表与写模式 / 去重业务键 / 终态条件 / 新鲜度 / 应覆盖实体范围（如日线收盘后为终态、openvlab IV 为时点快照、tick 落盘即定稿）；
- 建议落库为 `option.db` 中的 `data_storage_rule` 表（或启动时从配置文件加载），与 §6.5 就绪表同库、便于对账。**一取数单元一行**（字段以 `库表设计.md` §3.2 为准，此处同步）：

```sql
-- option.db（与库表设计 §3.2 对齐）
CREATE TABLE data_storage_rule (
    id INTEGER PRIMARY KEY AUTOINCREMENT,      -- 仅标识写入先后
    source_key   TEXT,     -- 单元唯一ID（= data_readiness.source_key，对账主键）
    table_ref    TEXT,     -- 落到哪张物理表（index_daily / contract_daily / option_iv…）
    display_name TEXT,     -- 中文名
    cadence      TEXT,     -- 分档：daily / realtime / static（决定就绪判据走哪条分支）
    authority    TEXT,     -- 权威主源（tbpy/openvlab/sina/manual/broker）
    fallback     TEXT,     -- 降级链（如 'tbpy,sina'；取不到按序退）
    schedule     TEXT,     -- 何时拉（post_close / intraday / low_freq / event）
    window_n     INTEGER,  -- 每次拉的尾巴窗口 count（index_daily=300；实时档留空）
    biz_key      TEXT,     -- 业务去重键（如 'index_code,trade_date'；= 表 UNIQUE 列）
    store_mode   TEXT,     -- 落库模式：incremental_upsert / full_window_rewrite / append_snapshot（实时快照）
    terminal_cond TEXT,    -- 终态条件（daily: 'now>品种收盘'；realtime:'n/a'；static:'存在即终'）
    max_age_sec  INTEGER,  -- 实时档新鲜度窗口（realtime 用；超窗判 STALE）
    expect_scope TEXT,     -- 应有清单枚举源（如 'product_boundary.is_active=1' → 动态算 MISSING）
    required_fields TEXT,  -- 必填非空字段（字段级缺失检）
    enabled      INTEGER DEFAULT 1,
    remark       TEXT,
    create_time  TEXT, update_time TEXT,
    UNIQUE (source_key)  -- 一取数单元一行
);
```
- 该清单以 `expect_scope` 动态枚举应有实体、驱动 §6.5 登记表的应到 vs 实到对账与终态判定，是阶段二"完整性/终态性"检查的前提。

## 十、输出（v2 草案）
- 判定四态：**PASS / FAIL / WARN / MISSING**（数据不足或质检未过一律 MISSING）。
- 综合日报四块：**A 开仓机会 / B 持仓处置 / C 组合风控 / D 提醒与待人工**（其中 D 须汇总 §6.5 登记表的「缺失 / 脏 / 非终态」项，源自数据就绪报告）。

## 十一、非功能需求
- **三阶段可独立调度**：阶段一/二可定时预跑，阶段三按需；彼此通过缓存 + 就绪登记表解耦。
- 缓存优先、tbpy 实时依赖最小化；单品种/单项取数失败只降级不崩；离线可跑（打时间戳）。
- 可观测：统一日志、**数据就绪门禁**与质检报告（prefetch 后缺失 / 脏 / 非终态项自动跳过并告警）；中央登记表提供"各表准备情况"看板。

## 十二、明确不做（范围外）
- 不接账户、不下单、不自动交易；不预测行情、不擅自改策略规则；不做任何裸卖。
