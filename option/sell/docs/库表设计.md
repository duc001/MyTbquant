# option.sell 库表设计（v2）

> 配套 `docs/需求文档.md` §六/§七。本系统**数据驱动**，库表是地基：先定 schema，再写三阶段流水线（拉取 → 检查 → 报表）与策略逻辑。
> 设计原则：
> 1. **业务数据**与**控制面**分离（逻辑上）：二者同处一个库文件 `option.db`，但用**不同的表**区分——业务数据表（§三）与控制面表（§二）互不混写，权限 / 生命周期也不同。
> 2. **价格口径两分**（承接需求文档 §二.1）：连续指数日线用**后复权**，仅供相对指标；合约 / 现货 / 权利金用**不复权**，供一切绝对价。混用即缺陷。
> 3. **日线类**业务表按 `pull_date`（归属交易日）分区 / 建索引；**快照类**（如 `option_iv`，见 §三.5）以 `snapshot_time` 为时间维度、不另设 `pull_date`。**实时数据两分**：盘口 tick（`bid`/`ask`/`last`、live premium、live IV）属"此刻"瞬时值，仅用于盘中实时选腿 / 定价，**不写为日线类业务表的定稿行**；确需保留的实时值（如 `option_iv` 的 IV 快照）以**快照表 + `snapshot_time` 完整时点**方式落库，不与日终定稿行混淆（详见 §五）。
> 4. **命名规范**：全系统**单一库文件** `option.db`（不再一表一库）；**表名**一律**两词以上**且**与 v1 严格区分**（v1 用单词名如 `spot`/`iv`/`position`/`capital`，v2 改为 `underlying_spot`/`option_iv`/`account_position`/`account_capital`/`trading_calendar`/`option_chain`/`index_daily`/`contract_daily` 等）；字段须定义清楚（口径 / 单位 / 来源）。
> 5. **可拉尽拉**：凡是数据源能取到的字段——即使当前策略暂未使用——也**一律落库存储**，不得因"暂时不用"而丢弃（避免日后分析时无数据）。
> 6. 旧 `strategies/sell_option/` 的表结构**不沿用**，本文件为全新首稿。

## 一、存储布局

```
option/sell/data/
└── option.db   # 全系统唯一库文件
    ├─ 业务数据表（§三，8 张）
    │   ├─ index_daily            连续指数日线（后复权）
    │   ├─ contract_daily         月度合约日线（不复权）
    │   ├─ underlying_spot        现货价（不复权）
    │   ├─ option_chain           期权链盘口 / 权利金（不复权）
    │   ├─ option_iv              隐含波动率（时点快照）
    │   ├─ trading_calendar       交易日历
    │   ├─ account_position       账户持仓（券商真实数据）
    │   └─ account_capital        账户资金 / 预算
    └─ 控制面表（§二，5 张）
        ├─ 全局配置表             系统级 KV 配置
        ├─ data_storage_rule     数据存储规则表
        ├─ data_state_check         数据状态核对表
        ├─ data_pull_detail         数据拉取明细表
        └─ product_info           品种信息表
```
> 库文件路径可由 `全局配置表` 的 `path.db` 键配置（默认 `option/sell/data/option.db`），不写死代码。业务表与控制面表均存于同一文件，逻辑上以"表"区分、互不混写。

## 二、控制面（库：option.db）

> 控制面 5 张表与业务数据同库（见 §一），但逻辑隔离、互不混写（设计原则 1）。其数据**非外部行情拉取**，而是由系统生成或 manual 维护。5 张表分两类职责：**配置 / 声明**（`data_storage_rule`、`全局配置表`、`product_info`）与**运行态**（`data_state_check` 状态登记 + `data_pull_detail` 拉取明细流水）。

### 2.1 全局配置表（KV 表）

- **用途**：系统级 KV 配置——数据源优先级与降级顺序（`source.*`）、预取时机（`schedule.*`）、门控严格度（`gate.*`）、库路径（`path.db`）等固定开关。阶段二 / 三只读消费。
- **数据源**：**manual**（手工维护 / 启动加载），非外部行情拉取。
- **抽取方法**：初始化时写入或 `UPSERT`；以 `key` 为主键，不加自增 id（见 §四）。

```sql
CREATE TABLE 全局配置表 (
    key         TEXT PRIMARY KEY,  -- 配置项名（含分组前缀，如 source.tbpy_priority / path.db）
    value       TEXT,              -- 配置值
    remark      TEXT,              -- 说明
    create_time TEXT,              -- 创建时间 YYYY-MM-DD HH:MM:SS
    update_time TEXT               -- 最后更新时间 YYYY-MM-DD HH:MM:SS
);
```
> KV 配置表以业务 `key` 为主键，**不加自增 id**（避免"重复 key"有后路）。

### 2.2 data_storage_rule（数据存储规则表）

- **用途（表名 `data_storage_rule`，中文名「数据存储规则表」）**：阶段零**声明性配置**——登记"每张业务表（取数单元）该从哪取、主源是谁、基础窗口与口径标记（`date_type` 等）"。它本身不落业务数据，是阶段一 / 二 / 三读取配置的**声明入口**。**配置与逻辑分离**：本表只提供**配置参数与分类标记**，并不承载核对规则本身；"应有条数怎么算、何时算终态、什么算正常 / 异常"这些**逻辑由检查程序依据本表的标记实现**，结果写入 `data_state_check`（见 §2.3）。本表是"声明"，检查程序是"规则引擎"。
  - **粒度**：一行 = 一个取数单元（以 `table_ref` 标识），即**一表一取数单元**（如 `index_daily` 一张表、一种后复权取数方式，覆盖 `product_info` 中全部 `main_index_symbol`（活跃主连））；数据源记于 `data_source` 单列（不设降级列）。
  - **字段语义**：
    - `table_ref`：落到哪张物理表；同时充当**取数单元唯一键**，以及与 `data_state_check` 对账的连接键（`UNIQUE`）。
    - `table_name`：表名（人读，区别于 `table_ref` 的物理表引用；如 '主连后复权日线'）。
    - `date_type`：数据类型的**元数据**（Tbquant 定义名 `bar` / `tick` / `static`，不翻译）。本表仅做分类标注，**下游各规则据此施管**：bar→日线终态判定、static→存在即终、tick→无终态（tick 档含实时瞬时值与快照，如 `option_iv`；快照写模式对应 `store_mode='append_snapshot'`，`date_type` 与 `store_mode` 维度不同、不冲突）。
    - `data_source`：主数据源（如 `tbpy`）。
    - `pull_method`：拉取方式（`post_close` / `intraday` / `event` / `low_freq`；`low_freq` 用于低频/静态单元如 `trading_calendar`）。
    - `pull_count`：每次拉取的**回溯条数**，**按每标的计**（index_daily=300 为整窗重拉；incremental_upsert 表仅取新 bar，`pull_count=1`；实时/static 档留空）。
    - `store_mode`：落库模式，取值各对应一档数据：`incremental_upsert`→不复权档（如 `contract_daily`）/ `full_window_rewrite`→后复权档（如 `index_daily`）/ `append_snapshot`→实时快照档（如 `option_iv`）。
    - `required_fields`：必填非空字段，字段级缺失检。
    - `status`：状态（1=有效/0=无效；有效=纳入应有效验，无效=旁路不拉不校验、不报错）。
  - **三阶段驱动（配置供程序消费）**：①阶段一按本表逐行（启用态）拉取并落库；②阶段二**检查程序**据 `date_type` 等标记实现核对——bar 档"应有条数" = `[bar_start_date, bar_end_date]` 区间内**实际交易日数**（依 `trading_calendar` 剔除节假日）× `product_info` 中全部 **`main_index_symbol` 实体数**——**不得用区间自然日跨度推算**（节假日无 bar 数据）；终态与正常 / 异常判定同样由检查程序按 `date_type` 实现（语义见 §2.3 四态 / §五）；③阶段三门控据 `data_state_check` 判定放行：**仅当 `status='normal'` 且 `bar_end_date` 已覆盖到所需交易日**才放行，否则（区间未覆盖 / `init` / `fetching` / `abnormal`）阻塞或等待。
  - **与 `data_state_check` 的关系（配置面 vs 状态面）**：两表经 `table_ref` 关联。`data_storage_rule` 是**被监控表的声明**（配置面）；`data_state_check` 是**检查程序依据本表声明、对每张表核对后的逐表状态登记**（状态面）。本表不定义"应有"的推导公式，只给出声明性参数（`date_type` / `pull_count` / `product_info` 关联等），具体"应有条数 / 终态 / 正常·异常判定"由检查程序实现，结果写回 `data_state_check`（status / last_detail_id 等）；对不上的即数据异常（见 §2.3 四态）。
  - **单一声明源（非规则源）**：§三 各表"用途 / 数据源 / 抽取方法"仅为人读说明，其**声明性取值**（数据源 / 窗口 / 写模式）以本表为准，冲突优先本表；但**核对规则（应有推导、终态与正常异常判定）不在本表**，由检查程序实现（见 §2.3 / §五）。

- **数据源 / 维护**：**manual**（设计期固化），随 schema 设计写入、状态 `status`；系统启动加载为期望基线。

- **一致性约束**：各业务表须按 §四 在其上建立 `UNIQUE` 约束以保证去重（本表不另存去重键）；`store_mode` / `date_type` 取值须与对应业务表实际取数 / 存储方式一致。

```sql
CREATE TABLE data_storage_rule (
    id INTEGER PRIMARY KEY AUTOINCREMENT,            -- 自增主键
    table_ref    TEXT UNIQUE,   -- 物理表引用（取数单元唯一键 + 对账连接键）
    table_name   TEXT,          -- 表名（人读）
    date_type    TEXT,          -- 数据类型
    data_source  TEXT,          -- 主数据源
    pull_method  TEXT,          -- 拉取方式
    pull_count   INTEGER,       -- 每标的回溯条数（实时档留空）
    store_mode   TEXT,          -- 落库模式
    required_fields TEXT,       -- 必填非空字段清单（逗号分隔列名）
    status       INTEGER DEFAULT 1,  -- 状态（1=有效/0=无效）
    remark       TEXT,          -- 备注
    create_time  TEXT,          -- 创建时间
    update_time  TEXT           -- 更新时间
);
```

> **示例（每个取数单元一行，仅列关键字段）**
> - **`index_daily`（主连后复权日线）**：`table_ref='index_daily'`、`date_type='bar'`、`data_source='tbpy'`、`pull_method='post_close'`、`pull_count=300`（每标的 300 条）、`store_mode='full_window_rewrite'`（`flag=RolloverBackWard`、全批共用 `adj_ref_date`，**非增量**保证单锚）。

### 2.3 data_state_check（数据状态核对表）

- **用途（表名 `data_state_check`，中文名「数据状态核对表」）**：`data_storage_rule` 所登记各取数单元的**逐表运行状态登记**（按 `table_ref` 1:1 对账）。每行记录该表**当前已就绪的数据区间 `[bar_start_date, bar_end_date]`**、**当前状态**（`status`，四态见字段语义）与**最近一次明细引用**（`last_detail_id` → `data_pull_detail.id`）。回答"这张表的数据是否准备完毕且正确"：`normal` 放行 / `abnormal` 阻塞 + 报警 / `init`·`fetching` 等待。本身是**状态面**：只沉淀核对结论，**不存明细**——拉取日期、实拉条数、`err_msg` 等一律记入 `data_pull_detail`（见 §2.4）；核对规则由检查程序实现（见 §2.2）。
  - **字段语义**：
    - `id`：自增主键，仅标识写入先后。
    - `table_ref`：本表主键（= `data_storage_rule.table_ref`，两表经此 1:1 对账），`UNIQUE`。
    - `bar_start_date`：本状态覆盖的数据**起始交易日**（归属日 `YYYY-MM-DD`）；对 bar 档即 bar 区间起点，对 tick/static 档表示其数据覆盖的日期范围（或留空，由新鲜度 / 完整性判定，见 §五）。
    - `bar_end_date`：本状态覆盖的数据**结束交易日**（通常为最新已就绪 `trade_date`）；与 `bar_start_date` 共同标识"已核对的是哪段数据"，而非拉取动作日。
    - `status`：**四态状态机**（简化，驱动全部门控）。取值：`init`（初始化：已登记、待拉取）→ `fetching`（拉取中：含校验中、盘中形成中 bar 尚未定稿，视为"尚未准备完毕"）→ 终局之一：`normal`（数据正常：拉取完成且校验通过、终态、**可放行**）/ `abnormal`（数据异常：缺数据 / 脏数据 / 校验不通过，**阻塞 + 报警**）。门控口径：仅 `normal` 放行；`init` / `fetching` 等待；`abnormal` 阻塞。
    - `last_detail_id`：指向 `data_pull_detail.id` 的**最近一次明细引用**；检查程序每轮动作后 upsert 本表并把本次明细行 `id` 写入此列，状态表借此关联到"当前结论来自哪次拉取"，错误 / 计数等明细全部从 `data_pull_detail` 读取，本表不存 `err_msg`。
  - **与 `data_storage_rule` 的关系（状态面）**：本表给**核对结论**（status / last_detail_id 指针），`data_storage_rule` 给"声明"（被监控表 + 参数）。"应有"推导与"正常 / 异常"判定由**检查程序**按 `date_type` 实现（bar：区间内实际交易日数（`trading_calendar` 剔除节假日）× `product_info` 全部 `main_index_symbol` 实体数，勿用自然日跨度；tick：新鲜度；static：完整性），对不上的即 `abnormal`（见 §2.3 四态 / §五）；检查程序内部比对"应有 vs 实有"后只暴露结论（状态 + 明细指针，错误明细在 `data_pull_detail`），不持久化实有计数。
  - **不使用外键**：`data_state_check` ↔ `data_storage_rule` 仅以业务键 `table_ref` 软引用（1:1），`data_state_check.last_detail_id` ↔ `data_pull_detail.id` 亦为软引用；`id` 仅表写入先后、随 upsert 会变，挂外键会悬空，故两表（及对账明细）以业务键 / id 软关联、无需外键。

- **数据源 / 写入**：**系统生成（检查程序产出）**——阶段一创建行置 `init`、启动拉取置 `fetching`，阶段二（校验）完成置 `normal` / `abnormal`；异常时检查程序可重试，每次重试作为新动作行记入 `data_pull_detail`（以 `pull_time` 区分），状态表仅以 `table_ref` upsert 刷新当前态与 `last_detail_id`；每轮预取 / 校验后 upsert。

```sql
CREATE TABLE data_state_check (
    id INTEGER PRIMARY KEY AUTOINCREMENT,   -- 自增主键
    table_ref TEXT UNIQUE,                  -- 本表主键（= data_storage_rule.table_ref，1:1 对账）
    bar_start_date TEXT,                    -- 覆盖的数据起始交易日
    bar_end_date TEXT,                      -- 覆盖的数据结束交易日（最新已就绪 trade_date）
    status    TEXT,                         -- 四态状态机：init→fetching→(normal|abnormal)；仅 normal 放行
    last_detail_id INTEGER,                 -- 最近一次明细引用（→ data_pull_detail.id）
    remark TEXT,                            -- 备注
    create_time TEXT, update_time TEXT,     -- 创建/更新时间
);
```

### 2.4 data_pull_detail（数据拉取明细表）

- **用途（表名 `data_pull_detail`，中文名「数据拉取明细表」）**：每次拉取 / 核对动作的**流水明细**，与 `data_state_check`（状态登记，每表一行）互补。后者只存"当前状态"，本表存"每次动作发生了什么"——拉取日期 (`pull_date`)、覆盖的数据区间、应有 / 实有计数、明细错误、拉取时间 (`pull_time`)。它是 `data_state_check` 的**审计轨迹**：某张表今天拉了几次、每次拉到多少、为何失败，全在本表可追溯；状态表只沉淀最终结论。
  - **粒度**：一行 = 一次拉取 / 核对动作（`table_ref` + `pull_time` 唯一确定）；同一 `table_ref` 可有多行（每日多次拉取 / 重试均留痕）。
  - **字段语义**：
    - `id`：自增主键。
    - `table_ref`：连接键（= `data_storage_rule.table_ref`），与状态表对账。
    - `pull_date`：**拉取日期**（`YYYY-MM-DD`，本次拉取动作发生的日期，动作日）——区别于业务表数据归属日 `trade_date`，也区别于状态表的数据就绪区间。
    - `pull_time`：本次拉取**完整时间戳**（`YYYY-MM-DD HH:MM:SS`，动作时刻）；`pull_date` 为其日期部分，本列用于排序 / 定位每次拉取动作，取代原 `fetch_at` / `validate_at` 的"动作时间"角色。
    - `bar_start_date` / `bar_end_date`：本次拉取覆盖的数据区间（对 bar 档即 bar 区间；对 tick/static 档表示其数据覆盖的日期范围，或留空由新鲜度 / 完整性判定，见 §五）。
    - `expected_n`：检查程序推导的**应有条数**（审计用）；算法：区间内**实际交易日数**（依 `trading_calendar.is_trading_day=1` 剔除节假日）× 活跃实体数，**不得用 `[bar_start_date,bar_end_date]` 自然日跨度推算**（节假日无 bar 数据）。
    - `actual_n`：本次**实拉条数**。
    - `status`：本次动作结果的**状态快照**（init / fetching / normal / abnormal），与状态表 `status` 同域。
    - `err_msg`：本次**明细错误的摘要**（缺失字段类别 / 异常品种计数 + 少量样本 / 失败原因）；**硬约束：不得逐条罗列全部异常项**——异常品种 / 行等列表过长时仅保留前若干样本并附"…共 M 条"计数，保持单行轻量、可消费；逐条排查由业务表反查，不塞入本字段。
    - `remark`：备注。
    - `create_time` / `update_time`：创建 / 更新时间。
  - **与 `data_state_check` 关系（流水 vs 状态）**：状态表（§2.3）每表一行沉淀"当前是否 ready"，本表每表多次一行留痕（粒度见上）。检查程序每轮拉取 / 校验后**双写**：既 upsert 状态表（`table_ref` 行，刷新 `status` / 数据区间 / `last_detail_id`），也 insert 本表（新动作行，以 `pull_time` 唯一区分）。

- **数据源 / 写入**：**系统生成（检查程序产出）**——每轮拉取 / 校验动作完成（或失败）后 insert 一行。

```sql
CREATE TABLE data_pull_detail (
    id INTEGER PRIMARY KEY AUTOINCREMENT,   -- 自增主键
    table_ref TEXT,                         -- 连接键（= data_storage_rule.table_ref）
    pull_date TEXT,                         -- 拉取日期（动作发生日，非 bar 归属日 trade_date）
    pull_time TEXT,                         -- 拉取完整时间戳（YYYY-MM-DD HH:MM:SS，动作时刻）
    bar_start_date TEXT,                    -- 本次覆盖数据起始交易日
    bar_end_date TEXT,                      -- 本次覆盖数据结束交易日
    expected_n INTEGER,                     -- 应有条数（按交易日历剔除节假日后 × 活跃实体数，审计用）
    actual_n INTEGER,                       -- 实拉条数
    status    TEXT,                         -- 本次动作结果状态快照（init/fetching/normal/abnormal）
    err_msg     TEXT,                       -- 本次明细错误（摘要化，截断勿逐条罗列）
    remark TEXT,                            -- 备注
    create_time TEXT, update_time TEXT,     -- 创建/更新时间
    UNIQUE (table_ref, pull_time)           -- 防同批次重复 upsert
);
```

### 3.1 指数日线：index_daily

- **用途**：**主连后复权日线**（连续合约、服务端 `RolloverBackWard` 换月后复权）。注意本系统"指数"指**主连连续合约（888 后缀，如 `m9888.DCE` / `rb888.SHFE` / `IF888.CFFEX`）**，非股票指数；后复权在此即"换月后复权"，用于抹平主力换月跳空。**仅服务于相对指标**——收益率、波动率、趋势、ADX、区间位置；绝不用于任何绝对价（价格口径两分铁律，需求文档 §二.1）。
- **数据源**：
  - **主源（唯一已实现）**：`tbpy`——`tbpy.get_history_n(symbol, "1d", count, fields, flag=tbpy.QuoteFlag.RolloverBackWard)` 取**服务端后复权**日线，属**三阶段驱动**的「拉取」阶段（拉取 → 检查 → 生成报表，由 §2.2 `data_storage_rule` 驱动）。
  - **返回字段**（`get_history_n` 按 `fields` 返回对应列；tbpy 实测/文档化字段集：`open`/`high`/`low`/`close`/`volume`/`time`/`position`/`rollover`）：本表实际取 `time` + `open`/`high`/`low`/`close`/`volume` 六项——`time`（字符串 `YYYY-MM-DD 00:00:00`）→ 落 `trade_date`；`open`/`high`/`low`/`close`（后复权）→ 对应列；`volume`（手）→ 落 `volume`。`pre_close`/`amount`/`turnover`/`vwap` **不在 tbpy 文档化字段集内**，本表标 `[可拉尽拉]`，能否拿到以 tbpy 实返回为准、不与主调用强绑定。
  - **佐证**：`tbpy方法参考` §5 确认 `RolloverBackWard` 是连续合约唯一复权枚举，无独立"原始价" flag；与一、设计原则 2（价格口径两分）一致——本表只存后复权，原始价由 `contract_daily` 不复权表承载。
  - **拉取阶段为何只取后复权**：「拉取」阶段据 `data_storage_rule`（`table_ref='index_daily'`）只以 `RolloverBackWard` 请求后复权字段；原始价须另用 `flag=None`（`QuoteFlag.Null`）重调、本表不需要，故一次拉取即够。拉取结果经「检查」阶段 `data_state_check` 对账，再进「生成报表」。
  - **备选**：**新浪**（§七 Q1 开放项，待验证）。
- **字段语义**（参考 §2.2 `data_storage_rule` 字段语义格式）：
  - `id`：自增主键，仅标识数据写入先后（技术键，非业务键）。
  - `index_code`：主连连续合约代码（如 `m9888.DCE` / `rb888.SHFE` / `IF888.CFFEX`），本表业务键；对应 `data_storage_rule`（`table_ref='index_daily'`）覆盖的标的范围（`product_info` 全部 `main_index_symbol`）；落库以该键整段全量重写（`full_window_rewrite`）。
  - `trade_date`：交易日，`YYYY-MM-DD`。
  - `open` / `high` / `low` / `close`：开盘 / 最高 / 最低 / 收盘价（**后复权**，换月后复权；仅服务相对指标，绝不用于任何绝对价，价格口径两分铁律见一、设计原则 2）。
  - `pre_close`：昨收（后复权）[可拉尽拉]。
  - `volume`：成交量（手）。
  - `amount`：成交额（元）。
  - `turnover`：换手率(%) [可拉尽拉]。
  - `vwap`：均价（后复权）[可拉尽拉]。
  - `adj_ref_date`：复权锚定日（本批拉取日；同批同值），用于相对指标单锚一致性校验（§五 复权锚定）；全批共用同一锚，相对指标须在同一 `adj_ref_date` 窗口内计算，切勿跨锚混算（按批同锚天然避免）。
  - 约束：`UNIQUE(index_code, trade_date)`，同标的同交易日唯一，防意外重复插入。
  - **抽取方法**：阶段一每日盘后据 `data_storage_rule`（`table_ref='index_daily'`）预取 → `get_history_n(symbol, "1d", count=pull_count, fields, flag=RolloverBackWard)` 拉**调整后 OHLC**。`pull_count` 默认 **300 条**（≈1.2 年日线，覆盖 ADX / 波动率 / 区间百分位回看），由 `data_storage_rule.pull_count` 驱动。**落库方式 = `store_mode='full_window_rewrite'`**：整窗拉取（非仅拉新 bar）——因后复权须单锚一致，增量 append 会把新旧锚行混在同一窗口、换月后相对指标算错（机理见 §五 复权锚定）；事务内先 DELETE 该标的历史窗口、再 INSERT 本批全窗，幂等、同日重拉命中缓存跳过。**收盘后为终态**（由 `date_type='bar'` 派生，见 §2.2）。对照：不复权表 `contract_daily` / `underlying_spot` / `option_chain` 用 `store_mode='incremental_upsert'` 追加新 bar，后复权表不可增量、须整窗重写。

```sql
CREATE TABLE index_daily (
    id INTEGER PRIMARY KEY AUTOINCREMENT,            -- 自增主键，标识数据写入先后
    index_code   TEXT,          -- 主连连续合约代码，如 m9888.DCE / rb888.SHFE / IF888.CFFEX
    trade_date   TEXT,          -- 交易日 YYYY-MM-DD
    open         REAL,          -- 开盘价（后复权，换月后复权）
    high         REAL,          -- 最高价（后复权）
    low          REAL,          -- 最低价（后复权）
    close        REAL,          -- 收盘价（后复权）
    pre_close    REAL,          -- 昨收（后复权）[可拉尽拉]
    volume       REAL,          -- 成交量（手）
    amount       REAL,          -- 成交额（元）
    turnover     REAL,          -- 换手率(%) [可拉尽拉]
    vwap         REAL,          -- 均价（后复权）[可拉尽拉]
    adj_ref_date TEXT,          -- 复权锚定日（本批拉取日；同批同值，用于相对指标单锚一致性校验）
    UNIQUE (index_code, trade_date)
);
```

### 3.5 隐含波动率：option_iv

- **用途**：隐含波动率时点快照（非终态语义）。`iv` / `iv_atm` / `hv_*` / `iv_rank` / `iv_percentile` / `skew` 用于相对估值与择时（IV 高位卖、低位买）。业务上称"快照"，元数据归 `date_type='tick'` 档（实时、无终态），写模式 `store_mode='append_snapshot'`（见 §2.2）。
- **数据源**：**tbpy / `option_chain.iv` 派生**（逐合约 iv 聚合为标的级 IV / 平值 IV / 历史波动率）；备选 **openvlab**（含更全 IV 曲面时）。
- **抽取方法**：阶段一在交易时段 / 盘后按 `product_cd` 抓取 IV 快照 → `UNIQUE(product_cd, snapshot_time)` 真 upsert；**快照即时点，非收盘终态**（老化以 `snapshot_time` 日期部分判定，不另设 `pull_date`）。

```sql
CREATE TABLE option_iv (
    id             INTEGER PRIMARY KEY AUTOINCREMENT,  -- 自增主键，标识数据写入先后
    product_cd     TEXT,
    snapshot_time  TEXT,   -- 时点 YYYY-MM-DD HH:MM:SS（快照本质，非 trade_date）
    iv             REAL,   -- 隐含波动率（标的级，如平值）
    iv_atm         REAL,   -- 平值 IV [可拉尽拉]
    hv_20          REAL,   -- 20日历史波动率 [可拉尽拉]
    hv_60          REAL,   -- 60日历史波动率 [可拉尽拉]
    iv_rank        REAL,   -- IV 分位(0-100) [可拉尽拉]
    iv_percentile  REAL,   -- IV 百分位 [可拉尽拉]
    skew           REAL,   -- 偏度 [可拉尽拉]
    UNIQUE (product_cd, snapshot_time)
);
```

### 3.6 交易日历：trading_calendar

- **用途**：交易日历。驱动预取时机、终态判定、跨日老化、长假 / 破位提醒。
- **数据源**：**manual**（由本地 `manual_calendar` 逐日播种，已本地化，不再依赖 tbpy.is_holiday / 外部日历）。
- **抽取方法**：阶段一每日或低频预取 → 写入 `trade_date` + 衍生标志（月末 / 季末 / 年末 / 邻长假）→ `trade_date UNIQUE` 真 upsert；静态参考表，非逐日终态。

```sql
CREATE TABLE trading_calendar (
    id                    INTEGER PRIMARY KEY AUTOINCREMENT,  -- 自增主键，标识数据写入先后
    trade_date            TEXT UNIQUE, -- 交易日 YYYY-MM-DD
    is_trading_day        INTEGER,  -- 1 交易日 / 0 非
    is_month_end          INTEGER,
    is_quarter_end        INTEGER,  -- [可拉尽拉]
    is_year_end           INTEGER,  -- [可拉尽拉]
    prev_trade_date       TEXT,    -- 上一交易日 [可拉尽拉]
    next_trade_date       TEXT,    -- 下一交易日 [可拉尽拉]
    pre_long_holiday_days   INTEGER,  -- 距前一长假天数

);
```

## 四、字段约定

- **口径**：`（后复权）`仅用于相对指标；`（不复权）`用于绝对价。混合即缺陷（需求文档 §二.1）。`index_daily` 存**服务端后复权价**（换月后复权，来自 `RolloverBackWard`），其列注释标"（后复权）"；因后复权保值收益率，相对指标与锚定日无关（见 §三.1 / §五 复权锚定）。
- **单位**：价格=元；成交量=手；金额=元；`pct`/`_degree`=百分比；greeks 为原生值。
- **`[可拉尽拉]`**：表示数据源可取到、但当前策略暂未消费，仍**一律落库**，以备后续分析。
- **时间**：`trade_date` 与 `pull_date` **同义**，均为归属交易日 `YYYY-MM-DD`（设计原则 3 / §五"按 pull_date 分区"对二者一致适用）；`snapshot_time` = 完整时点（快照类）。
- **数值精度**：数值字段统一用 `REAL`（价格 / 金额 / 比率 / greeks 等），**不**采用 INTEGER 最小单位方案（如"分"），以免引入 100 倍换算错误、且仍无法精确表达 0.0001 元价格。REAL 的浮点残差在**比较 / 累加处做好控制**：金额按业务精度四舍五入（如到分）、价格按最小变动价位；避免大量浮点连加；相等比较用 epsilon。
- **自增 id**：所有业务数据表首列统一加 `id INTEGER PRIMARY KEY AUTOINCREMENT`，仅用于标识数据写入先后、便于排查；原业务复合/单列主键**一律降为 `UNIQUE` 约束**保留去重语义（控制面 `data_storage_rule` / `data_state_check` 同样必须补 `UNIQUE`，否则 id 抢占主键后去重凭空消失）。**例外**：KV 表 `全局配置表` 与静态表 `product_info` 以业务键为 `PRIMARY KEY`，不加自增 id。
- **id 稳定即"先后"（重取纪律）**：`id` 要真实代表首次写入顺序，重取/重跑**必须用 `ON CONFLICT(业务 UNIQUE 键) DO UPDATE`（真 upsert，id 不变），禁用 `INSERT OR REPLACE`**（后者删+插会发新 id，打乱"先后"）。

## 五、关键关系与口径

- **三类时序数据约束（总览）**：本系统行情数据存在三类时序一致性问题，分别由下方专条约束——① **后复权锚漂移（事件驱动、对相对指标无碍）**：`index_daily` 后复权绝对水平**并非每拉必变**，仅当两次拉取间隔内发生换月时历史事件的水平才会重算漂移；但后复权保值收益率，**相对指标与锚无关**，且本表仅用于相对指标，故实际无碍（见『复权锚定』）；落库存后复权价 + `adj_ref_date`、相对指标单锚计算即可。② **盘中形成中 bar**：日线类 `trade_date == today` 行为收盘前临时值（见『终态性 / 盘中拉取』）；③ **实时数据瞬时性**：盘口 tick 仅盘中可获、只服务实时决策（见『实时数据分类』）。三者共同决定：哪些数据能落库、以何主键、何时为终态、相对指标须在同一锚 / 同一终态窗口内计算。
- **table_ref 关联（1:1）**：`data_state_check.table_ref` = `data_storage_rule.table_ref`，两表经此**一对一**关联（一个取数单元契约行 ↔ 一张表的当前状态行）；`data_state_check` 以 `bar_start_date` / `bar_end_date` 标识其核对覆盖的数据区间（而非拉取日），对账出"应有 vs 实有"。
- **品种关联**：业务表 `product_cd`（品种）/ `symbol`（合约）关联 `product_info.product_cd`，取乘数 / 保证金金额（单腿 `margin_per_lot` / 实际占用 `actual_margin_per_lot`，见 §2.5）。
- **时间维度 / 分区**：日线类业务表含 `pull_date` / `trade_date`，跨日自动失效，不拿旧数据当新；**快照类**（如 `option_iv`）以 `snapshot_time`（YYYY-MM-DD HH:MM:SS）为时间维度，**不另设 `pull_date`**——其日期部分即归属日，承担老化 / 去重，无需重复列。控制面 `data_state_check` **不存 `pull_date`**，改以 `bar_start_date` / `bar_end_date` 标识其核对覆盖的数据区间（描述"齐了哪段数据"，而非"哪天拉的"）。
- **价格口径**：`index_daily` 后复权（相对指标），其余不复权（绝对价）——检查逻辑须严格分流。
- **终态性与四态映射**：日线类（`bar`）**收盘后为终态** → 检查程序据此将 `status` 置 `normal`；盘中 `trade_date==today` 的形成中 bar 视为"尚未定稿"，`status` 停留在 `fetching`（等待），不消费未定稿数据，收盘后重拉定稿再转 `normal`。`option_iv`（`tick`）快照即时点、无终态语义，按新鲜度判 `normal`/`abnormal`；`static`（如 `trading_calendar`）存在即终。`normal`/`abnormal` 的具体判定由检查程序按 `date_type` 实现（见 §2.3）。
- **实时/静态档就绪判据（检查程序实现）**：`date_type='tick'`（实时/快照，如 `option_iv`）不以计数核对，而以**新鲜度**为就绪判据——当日内须已产生快照且 `snapshot_time` 落在最近交易时段内，越窗即判 `abnormal`；具体新鲜度窗口由检查程序配置。`date_type='static'`（如 `trading_calendar`）以**完整性**核对（覆盖预期区间 / 存在即终），非每日计数，判 `normal`/`abnormal`。
- **盘中拉取（形成中 bar）处理**：日线类在交易时段内拉到的 `trade_date == today` 行是**形成中 bar**（`close` 非当日最终收盘），**不得直接用于相对指标 / 绝对价结论**。三层处理：(a) **读侧**：对 `trade_date == today` 且未过收盘时点的行硬判"形成中"、排除出 #3 市况 / #10 否决等指标，最新有效点取上一已完成交易日；(b) **门控**：阶段二判 `bar` 收盘前为形成中，将当日 `data_state_check.status` 维持在 `fetching`（视为尚未定稿、等待），阶段三不消费 `fetching` 数据，盘中只产出"待收盘 / 粗筛"结论、绝不硬下绝对价；(c) **回填**：收盘后阶段一以 `use_cache=False` 对刚收盘交易日**强制重拉回填**，定稿后检查程序将 `status` 转 `normal`。盘口 tick（`option_chain.bid/ask`、`option_chain.last`、premium）是**某时刻真实快照**，仅用于盘中实时选腿 / 定价，不得替代日线 `close` 作历史绝对价基准。
- **实时数据（盘口 tick / 快照）分类**：实时数据分两类处理——(a) **瞬时盘口 tick**（`option_chain.bid/ask/last`、live premium、live IV）：盘中实时选腿 / 定价 / 盘口检查（#1）用之，纯瞬时、**不落日线类业务表**，扫描结束即弃；(b) **需留痕的实时值**：以**快照表 + `snapshot_time`（YYYY-MM-DD HH:MM:SS）**方式落库（范例 `option_iv`），用于复盘 / 审计 / 跨日比对，且**不与日终定稿行互相覆盖**——快照按 `snapshot_time` upsert、日线按 `pull_date`/`trade_date` upsert，两套主键互不干涉。若日后还需保留"扫描时刻盘口快照"，应**单开快照表**（如 `option_quote_snapshot`），禁止写回 `option_chain` 日终行。
- **复权锚定（后复权序列的时点依赖）**：`index_daily` 的后复权**绝对水平**不是 `(index_code, trade_date)` 的唯一事实——它依赖「复权锚定日（拉取日）」：锚定日不同（期间发生换月），历史后复权**水平**会重算而漂移（见下方实证）。但**后复权是乘性平移、保值收益率**：同一连贯拉取内任意两日之比 = 真实收益率，与锚定日无关。本表**仅用于相对指标**（收益率 / ADX / 区间位置），故锚漂移对其**无实质影响**；只有"拿后复权绝对价当价格"才会出错（已被"价格口径两分"铁律禁止）。处理：(a) 落库存**服务端后复权价 + `adj_ref_date`**（锚定日标记），弃用原始价 / 调整因子方案——tbpy `QuoteFlag` 仅 `RolloverBackWard` 一个复权枚举、无独立"原始价" flag（原始价需 `flag=None` 额外拉取，且对相对指标无益），故只拉一次 `RolloverBackWard` 即可；(b) 相对指标须在**同一 `adj_ref_date` 窗口**内计算，切勿跨不同锚定日的行混算（按批同锚天然避免）；(c) 不复权表（`contract_daily` / `underlying_spot` / `option_chain` 的 OHLC）是真实成交价、不随锚定日变，无此问题。（**实证**：本机 `strategies/sell_option/sell_option/data/daily.db` 的 `index_daily` 表中，`m9888.DCE` 在 `2026-09-30` / `10-08` / `10-09` 三次拉取的 298 个共同历史日，后复权收盘价**完全一致**——间隔内无换月事件，印证"水平漂移是事件驱动、非每拉必变"；即便有换月导致水平漂移，相对指标仍与锚无关。）
